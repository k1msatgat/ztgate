# 0002. 핸드셰이크는 직접 짜고, 암호 묶음은 협상하지 않고 고정한다

- 상태: 채택
- 날짜: 2026-10-13 (세션 암호화, 프로토콜 v3 `22a3e48`). v9(`7cca575`)에서 핸드셰이크의 모양이 바뀌었다 (0003, 0004)

## 맥락

ZTNA 서버는 "이 기기가 맞는가" 와 함께 "이 기기가 지금 믿을 만한 상태인가"(포스처)를 접속할 때와 접속한 뒤 계속 본다. 기기 ID, 포스처, 서버가 내려 주는 터널 설정(주소, 경로, DNS)이 핸드셰이크와 keepalive 에 실려야 하고, Linux 서버(OpenSSL)와 Windows 클라이언트(CNG)가 같은 바이트를 만들어야 한다.

## 결정

- 메시지: `REQ` → `CHALLENGE`(nonce, 서버 공개키) → `AUTH`(일회용 공개키, 감싼 기기 ID 와 포스처, 기기 키의 mac) → `RES`(일회용 공개키, 암호화된 터널 설정).
- 암호: P-256 ECDH(일회용), HKDF-SHA256(salt = 기기 키, 주고받은 패킷의 해시를 섞는다), AES-256-GCM. 협상은 없다. 바꾸려면 프로토콜 버전을 올린다.
- 세션 패킷: 64bit `counter` 가 GCM nonce 이자 재전송 창의 순번, 헤더 전체가 tag 의 범위.
- 같은 소스(`lib/common`)를 양쪽이 빌드하고, 양쪽 `selftest` 가 같은 표준 벡터를 통과하는 것을 통한다는 근거로 삼는다.

## 검토한 다른 길

- **IKEv2 (strongSwan 등)** — 표준이고 검토된 구현이 있다. 포스처를 실으려면 EAP 나 알림 페이로드를 확장해야 하고, 협상과 SA 관리의 크기에 비해 여기서 쓰는 부분이 작다.
- **WireGuard / Noise IK** — 1왕복이고 단순하다. 정적 공개키로만 신원을 말하므로 기기 ID 와 포스처를 핸드셰이크에 얹을 자리가 없고, 서버 쪽 판정을 따로 붙여야 한다.
- **DTLS** — 표준 TLS 라이브러리를 쓸 수 있지만, 인증서와 협상을 함께 떠안는다.

## 결과

- 메시지가 짧고 다운그레이드 공격면이 없다. 포스처와 터널 설정이 인증된 같은 메시지에 실린다.
- **이 조립은 외부 검토를 받은 적이 없다** (README "알려진 제약"). 시험이 보여 주는 것은 의도한 대로 동작한다는 것까지다.
- 세션 중 키 교체가 없어 키 수명이 다하면 끊고 다시 연다 (그 사이 왕복 두 번의 패킷을 잃는다).
- 표준과의 차이는 README 의 "표준 프로토콜과의 대조"에 있다.
