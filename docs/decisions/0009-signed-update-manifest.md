# 0009. Windows 자동 업데이트는 서명한 매니페스트만 따른다

- 상태: 채택
- 날짜: 2026-10-25 (`4f2aa2e` 서명 도구, `c7d7185` 서비스의 확인)

## 맥락

0.9.1 의 자동 업데이트는 정책 `UpdateUrl` 의 매니페스트(version, msi, sha256)를 TLS 로 받아, MSI 가 그 해시와 같으면 SYSTEM 으로 설치했다. 해시가 매니페스트와 같은 곳에서 오므로, 업데이트 서버(나 그 TLS 인증서)를 차지한 쪽은 모든 PC 에 아무 MSI 나 설치시킬 수 있었다. 코드 서명 인증서는 없다.

## 결정

- 매니페스트에 `sig` 를 붙인다: `"ztgate update v1\n" + version + "\n" + sha256` 에 대한 ECDSA P-256 (r | s). `tools/update/ztgate_update_sign.py` 가 만들고, 서명 키는 업데이트 서버 밖에 둔다.
- 서비스는 정책 `UpdatePublicKey`(128 hex, 키를 바꾸는 동안은 둘)의 키 가운데 하나로 서명이 맞는 매니페스트만 따르고, 맞지 않으면 버전도 믿지 않는다. 공개키가 없거나 틀리면 업데이트하지 않는다.
- MSI 의 주소는 서명하지 않는다. 해시가 내용을 정하므로 다른 곳에 올려 두어도 된다.

## 검토한 다른 길

- **MSI 의 Authenticode 를 WinVerifyTrust 로 확인** — Windows 의 표준이고 SmartScreen 경고도 사라진다. 코드 서명 인증서가 있어야 한다. 인증서가 생기면 이것을 더한다.
- **TLS 만 (그대로)** — 업데이트 서버 하나가 모든 PC 의 SYSTEM 권한이 된다.
- **TUF 같은 업데이트 프레임워크** — 동결 / 혼합 공격까지 막지만, 역할 키와 메타데이터가 여럿이다.

## 결과

- 업데이트 서버를 차지해도 서명 키 없이는 설치시키지 못한다. 예전에 서명한 매니페스트를 다시 내놓는 것은 지금보다 낮은 버전이라 아무 일도 하지 않는다.
- 업데이트를 내놓지 않고 멈춰 두는 것(동결)은 막지 못한다. MSI 자체는 여전히 서명되지 않은 파일이다.
- **`UpdateUrl` 만 둔 0.9.2 의 PC 는 공개키 정책을 더해야 업데이트된다.**
- `vpn_client selftest` 가 도구(openssl)로 만든 서명을 CNG 로 확인한다 — 두 구현이 같은 것에 서명하고 확인한다는 근거.
