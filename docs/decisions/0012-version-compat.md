# 0012. 서버를 먼저 올리고, 서버는 한 버전 아래의 클라이언트도 받는다

- 상태: 채택
- 날짜: 2026-10-27

## 맥락

헤더의 버전 바이트가 `PROTOCOL_VERSION` 과 다르면 서버도 클라이언트도 패킷을 말없이 버렸다. 그래서 버전을 올릴 때마다 서버와 모든 클라이언트를 한꺼번에 바꿔야 했고(CHANGELOG 첫 문단), 한쪽이 먼저 올라가면 사용자는 "서버가 답하지 않습니다"만 봤다. 원인이 버전인지 네트워크인지 알 수 없었고, Windows 의 자동 업데이트는 6시간 뒤에야 돌았다. 상용화 검토에서 "lockstep upgrade" 로 높음이었다.

## 결정

- **올리는 순서는 서버가 먼저다.** 클라이언트는 수천 대이고 자동 업데이트로 며칠에 걸쳐 따라온다. 서버는 한두 대이고 운영자가 올린다.
- **서버는 `[PROTOCOL_VERSION_MIN, PROTOCOL_VERSION]` 를 받는다.** 다음에 버전을 올리는 변경(v10)은 `PROTOCOL_VERSION_MIN` 을 9 로 두고, 서버에서 v9 의 모양도 읽고 쓴다(피어마다 버전을 기억한다). 그 다음 버전(v11)에서 v9 를 뗀다. 지금은 v9 하나뿐이라 둘이 같다. 아직 없는 v10 을 위한 분기를 미리 만들지 않는다.
- **범위 밖의 클라이언트에게는 말해 준다.** 범위 밖 버전의 `REQ_HANDSHAKE` 에 서버는 `VERSION`(헤더 | min | max, 10B)으로 답한다. 이 모양은 앞으로 바꾸지 않고, 클라이언트는 헤더의 버전을 보기 전에 종류가 `VERSION` 인지 먼저 본다. 그래서 어느 쪽이 먼저 올라가도 원인이 보인다.
  - Windows 는 서버가 더 새 버전만 받으면 "이 PC 를 올린다"로 보여 주고 서비스가 업데이트 확인을 바로 띄운다(10분에 한 번까지). 서버가 더 오래되었으면 "서버를 올린다"로 보여 준다.
  - 서버는 그런 패킷을 `version_mismatch` 로 센다. 운영자는 아직 올라오지 않은 클라이언트가 얼마나 남았는지 지표로 본다.
- **메시지 종류를 더하는 것은 버전을 올리지 않는다.** 모르는 종류는 양쪽 모두 버린다(`DISCONNECT`, `VERSION` 이 그렇게 들어왔다). 버전은 이미 있는 메시지의 모양이 바뀔 때만 올린다.

## 검토한 다른 길

- **지금 v8 클라이언트도 받기** — v8 은 핸드셰이크에 기기 ID 를 평문으로 싣는다(v9 가 막은 것). 그것을 다시 받으면 v9 가 없앤 노출을 서버가 계속 허락하게 된다. 그리고 지금 쓰이는 Windows 클라이언트는 모두 v9(0.9.3)다.
- **협상(클라이언트가 여러 버전을 내밀고 서버가 고르기)** — 암호 묶음은 협상하지 않기로 했고(ADR 0002) 버전도 같은 이유로 고른다. 협상은 내려가기 공격의 자리를 만든다. 서버가 받는 범위를 알려 주는 것은 어느 쪽도 내려가게 하지 않는다.
- **`VERSION` 에 서명하기** — 버전이 다른 클라이언트와 서버는 같은 서명 방식을 쓴다고 볼 수 없다. 위조된 `VERSION` 은 화면에 잘못된 안내를 띄울 수 있을 뿐이고, 클라이언트는 그것으로 멈추지 않고 계속 다시 시도한다. 진짜 답이 오면 그것을 따른다(확인할 수 없는 `DENY` 와 같은 처리).

## 결과

- 버전이 다르다는 것이 "응답 없음" 대신 사유로 보인다. 위조된 `VERSION` 한 통으로 접속을 막을 수는 없다.
- 다음 버전부터 서버를 먼저 올려도 남은 클라이언트가 끊기지 않는다. 그것은 그 버전을 만들 때 v9 의 모양을 함께 다루는 일이 있어야 지켜진다 — `auth_check.py` 의 "previous protocol version" 시험이 그때 `VERSION` 대신 수락을 기대하도록 바뀌어야 한다.
- Linux 클라이언트는 `VERSION` 을 읽지 않는다(예전처럼 응답 없음으로 본다).
