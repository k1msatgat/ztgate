# 0007. 사용자 토큰은 서버가 IdP 에 묻지 않고 확인하고, DPoP 로 기기에 묶는다

- 상태: 채택
- 날짜: 2026-10-24 (DPoP `511111d`). 사용자 로그인(LOGIN) 자체는 2026-10-15 (프로토콜 v5, `05e41d4`)

## 맥락

기기 신원(0004) 위에 "지금 이 기기를 누가 쓰는가"를 얹어, ACL 규칙에 사용자 / 그룹 조건을 건다. 회사의 IdP(Keycloak, Entra ID, Okta)가 사용자 인증을 맡는다. 서버는 패킷 경로에 있고, IdP 가 잠깐 죽었다고 터널이 멈추면 안 된다. 클라이언트가 받은 토큰이 다른 기기로 새어 쓰이는 것도 막아야 한다.

## 결정

- 클라이언트가 IdP 에서 받은 액세스 토큰(JWT)을 세션 안의 `LOGIN` 으로 보낸다. 서버는 IdP 에 묻지 않고, 받아 둔 JWKS 로 서명(RS256 / ES256, `kid` 와 키 종류가 맞아야 한다)과 `iss` / `aud` / `exp` / `nbf` 를 본다. JWKS 는 `ztgate_jwks.py`(타이머, 15분)가 받아 준다.
- 토큰에 `cnf.jkt` 가 있으면 DPoP(RFC 9449) 증명이 함께 와야 한다: 그 키의 서명, `htm`/`htu`, `iat` 창, `ath`(이 토큰의 해시), 한 번만 쓰는 `jti`. 증명 키는 기기가 가진다 (Windows 는 서비스의 키, TPM 우선). `idp.conf` 의 `dpop required` 는 묶이지 않은 토큰을 거절한다.

## 검토한 다른 길

- **토큰 검사(introspection, RFC 7662)를 IdP 에 매번** — IdP 에서 막은 사용자가 바로 막히지만, IdP 가 패킷 경로의 의존이 된다.
- **mTLS 로 묶기 (RFC 8705)** — 클라이언트 인증서 배포가 필요하다. 터널이 TLS 가 아니다.
- **묶지 않기** — 새어 나간 토큰을 다른 기기에서 쓸 수 있다. 다만 세션을 열려면 등록된 기기의 키도 있어야 한다.

## 결과

- IdP 가 멈춰도 이미 받은 토큰은 `exp` 까지 쓰인다. **IdP 에서 막은 사용자도 `exp` 까지는 쓰인다** — 토큰 수명을 짧게 둔다.
- 묶는 것은 IdP 가 DPoP 를 해 줘야 하므로 기본은 묶이지 않은 토큰도 받는다. CI 는 Keycloak 을 `--features=dpop` 로 띄워 실제 묶인 토큰을 확인한다.
- `jti` 는 최근 512개를 기억한다. 짧은 시간에 그보다 많은 로그인이 오면 밀려난 `jti` 를 다시 쓸 수 있다 (증명은 세션 안에서만 오가므로 엿볼 수 없다).
