# 0014. 서버는 MCP 의 배포기가 원격의 ref 를 장비에서 패키지로 빌드해 깔고, 떨어지면 스스로 되돌린다

- 상태: 채택
- 날짜: 2026-10-31

## 맥락

AI 클라이언트는 ssh stdio 의 MCP 로 서버를 다룬다. 시험과 운영을 위해 고른 ref 의 서버를 올리고, 새 서버가 일하지 않으면 이전 것으로 돌아갈 수 있어야 했다. 그때까지 서버를 바꾸는 길은 장비에서 `mcp/install.sh` 를 다시 돌리는 것뿐이었다. 그것은 작업 트리의 무엇이든 깔았고, 되돌릴 이전 판을 남기지 않았다.

모양이 뻔하지 않은 까닭은 넷이다.

- 배포할 코드가 배포하는 코드를 바꾼다. `ztgate_ctl` 은 패키지 안(`/usr/sbin`)에 있다. 배포를 ctl 의 명령으로 두면, 배포 기능 이전의 ref 로 내려가는 순간 배포와 되돌리기가 함께 사라진다.
- 오래 걸린다. 가져오기, 빌드, 설치, 15초의 검사, 떨어지면 되돌리기와 두 번째 검사까지 한 호출에 넣으면 MCP 호출과 ssh 가 먼저 끊길 수 있다. 그 사이에 ctl 자신과 서버가 바뀐다.
- 권한의 경계가 바뀐다. 그때까지 MCP 계정이 할 수 있는 일은 ctl 의 `COMMANDS` 가 전부였다. 배포는 정의상 새 root 코드를 돌린다.
- 장비가 작고 운영 중이다. 빌드가 VPN 의 데이터 경로에서 CPU 와 메모리를 뺏으면 안 된다.

## 결정

- **배포기는 패키지 밖에 산다.** `mcp/deploy.cjs` 를 `mcp/install.sh` 가 MCP 서버와 함께 `/opt/ztgate-mcp/libexec/ztgate-deploy` 에 놓는다. ctl 과 나란한 두 번째 sudo 헬퍼이고, sudoers 는 둘 다 인자 없이만 연다. 어느 ref 로 내려가도 배포기는 남는다. `install.sh` 는 이제 MCP 와 배포기만 깔고, 서버는 패키지로만 깔린다.
- **도구는 셋이다.** `deploy {ref, accept?}` 와 `deploy_rollback {to?, accept?}` 는 작업을 적고 바로 작업 id 를 준다. `deploy_status {job?, wait_seconds ≤ 150}` 가 끝날 때까지 기다린다. 배포와 되돌리기는 같은 작업(대상, 출발점)이고 실패 처리 경로도 하나다.
- **작업은 이름이 고정된 일회성 유닛이다.** 배포기는 `systemd-run --unit=ztgate-deploy` 로 자신을 띄운다. systemd 는 같은 이름의 유닛을 둘 만들지 않으므로 그것이 "한 번에 하나" 다. 남는 잠금 파일이 없다. 유닛은 ssh 세션 밖에서 돌아, MCP 가 끊기거나 ctl 이 바뀌거나 서버가 다시 떠도 계속된다. 두 번째 요청은 같은 대상이면 도는 작업을 돌려주고(`already_running`), 다르면 거절한다.
- **지금 설치된 것은 적지 않는다.** 매번 패키지 DB(`rpm -q`, `dpkg-query`)에서 읽는다. 적는 것은 추가만 하는 사실이다. 작업마다 `request.json` 과 `events.jsonl` 이 있고, 단계는 사건을 전이 표로 접어 끌어낸다. 끝이 적히지 않았는데 유닛이 없으면 읽을 때 `interrupted` 로 보인다. 이전 것은 `history.jsonl`(검사를 통과한 설치마다 한 줄) 에서, 지금 것을 깐 줄의 `from` 이다. 되돌려진 시도는 이전 것이 되지 않는다.
- **커밋마다 다른 패키지 판.** `packaging/build.sh` 에 `SNAPSHOT=<커밋 시각>.g<커밋 12자>` 를 주면 rpm 은 Release `0.<SNAPSHOT>`, deb 는 `<ver>~<SNAPSHOT>` 다. 정식 릴리스(SNAPSHOT 없음)는 그대로이고, 같은 VERSION 의 정식 판보다 앞으로 정렬된다. 같은 커밋은 같은 판을 받으므로 보관 패키지를 다시 쓰고, 깔린 커밋을 다시 배포하면 `unchanged` 다.
- **설치는 `rpm -U --oldpackage` 와 `dpkg -i` 다.** dnf 와 apt 는 쓰지 않는다. 새 의존성이 필요한 판은 rpm 이 아무것도 바꾸기 전에 거절하므로 `failed`(장비 그대로)로 끝난다. 설치 전마다 `ztgate-backup` 을 돌리고 그 파일을 사건에 남긴다. 설정은 자동으로 되살리지 않는다. 되살리면 그 사이에 등록한 기기를 잃는다.
- **검사가 판정하고, 떨어지면 스스로 되돌린다.** 서버가 돌고 있었으면, 유닛이 15초 동안 같은 pid 로 재시작 없이 active 인지, `/proc/<pid>/exe` 의 sha256 이 패키지 안 `vpn_server` 와 같은지, UDP 에 버전 255 의 REQ 를 보내 `VERSION` 답이 오는지(ADR 0012, 이 답의 모양은 바뀌지 않는다) 본다. 언제나 새 `ztgate_ctl status` 가 되는지, 패키지 DB 가 대상인지, `server.key` 가 그대로인지 본다. 세션 수는 적기만 하고 판정에 쓰지 않는다. 하나라도 떨어지면 출발점 패키지를 다시 깔고 같은 검사를 한다. 결과는 `reverted` 이거나, 그것도 떨어지면 `broken` 이다. 멈춰 있던 서버는 띄우지 않는다.
- **설치와 검사 사이에는 ctl 이 서버의 start, stop, restart 와 auth_check 를 거절한다.** 표지 파일(`/run/ztgate-deploy/window`)은 그 작업의 유닛이 살아 있을 때만 믿는다.
- **부 서버에서도 배포한다.** 배포는 코드이고 동기화는 설정이다. 다만 대상의 `[PROTOCOL_VERSION_MIN, PROTOCOL_VERSION]` 가 지금 서버의 범위와 겹치지 않으면, 지금 붙은 클라이언트가 모두 끊기므로 `accept: ["protocol_break"]` 없이는 거절한다. 출발점이 배포기가 만든 패키지가 아니면(손으로 깔았거나 아무것도 없음) 되돌릴 수 없으므로 `accept: ["no_revert"]` 없이는 거절한다.
- **감사.** 요청마다 `admin` 사건(누가, 무엇을, 받았는지)을, 끝난 작업마다 `deploy` 사건(결과, 출발점, 대상)을 ctl 과 같은 감사 로그에 덧붙인다. `audit_log` 도구의 사건 목록은 ctl 의 `AUDIT_EVENTS` 와 같고, `mcp/surface.test.cjs` 가 두 목록을 맞춰 본다.

### 신뢰의 뿌리

이 장비의 root 권한은 `/etc/ztgate-deploy/deploy.conf` 의 `REPO` 에서 `BRANCHES` 와 `TAGS` 로 닿는 커밋에 있다. 그 ref 에 push 할 수 있는 사람이 곧 이 장비의 root 다. 지금은 GitHub 계정 `k1msatgat`, GitHub 자신, github.com 의 TLS 다. 같은 폴더에 `allowed_signers` 를 두면 그 키로 서명한 커밋만 깔고, 뿌리는 서명 키로 좁아진다.

- `deploy.conf` 는 root 소유이고 남이 쓸 수 없어야 하며, 서버 계정이 쓸 수 있는 `/etc/ztgate` 밖에 있다. KEY=VALUE 로만 읽는다.
- 호출한 쪽의 `ref` 는 네트워크에 닿지 않는다. 가져오기의 refspec 은 `deploy.conf` 에서만 나오고, SHA 로는 가져오지 않는다. GitHub 는 포크의 커밋도 부모 저장소 주소로 내주므로, SHA 로 가져오면 아무나 연 PR 의 코드를 root 로 돌릴 수 있다. 커밋 id 는 허용된 ref 에서 닿아야 한다.
- 가져오기와 판단은 root 소유의 bare 저장소(`/var/lib/ztgate-deploy/src.git`)에서 한다. root 의 git 은 훅 없이, 시스템과 전역 설정 없이, REPO 의 방식 하나만 열고 돈다. 가져오기 자체는 능력 없는(`CapabilityBoundingSet=`) 일회성 유닛에서 그 저장소만 쓴다.
- 빌드는 `ztgate-build` 계정이 `PrivateNetwork`, `ProtectSystem=strict`, `MemoryMax=450M`, `MemorySwapMax=0`, `CPUWeight=10`, `Nice=10` 의 일회성 유닛에서 `git archive` 의 tar 만 받아서 한다. root 는 끝난 뒤 나온 패키지 하나를 링크를 따르지 않고 root 의 보관소로 복사하고, 이름과 판이 기대한 값인지 본 뒤 그 복사본만 믿는다. **이것은 보안 경계가 아니다.** 그 소스로 만든 패키지는 어차피 root 로 `%post` 를 돈다. 정직한 소스의 버그(엉뚱한 곳을 지우는 Makefile, 메모리를 다 먹는 빌드)가 장비와 VPN 을 다치게 하지 못하게 하는 손해 제한이다.

MCP 계정을 차지한 쪽은 허용된 ref 에서 닿는 커밋 아무것이나(오래되어 취약한 것도) 깔고, 보관 패키지로 되돌리고, 위험을 `accept` 로 감수한다고 말할 수 있다. 원격의 주소, 허용 목록, 서명 요구, 빌드 명령과 환경은 바꿀 수 없고, 패키지 파일을 넣거나 배포기 자신을 바꿀 수도 없다.

## 검토한 다른 길

- **배포를 ctl 의 `COMMANDS` 에 넣기.** 표면은 가장 작다. 하지만 ctl 이 패키지 안에 있어서, 배포 기능 이전의 ref 로 내려가면 배포와 되돌리기가 함께 사라진다. 작업 도중 ctl 이 자기 파일을 바꾸는 문제도 생긴다.
- **CI 가 빌드하고 서명한 패키지만 깔기 (Windows 의 ADR 0009 처럼).** 장비는 빌드하지 않는다. 하지만 서명 키가 GitHub Actions 의 비밀이면 push 할 수 있는 누구나 워크플로를 고쳐 서명을 받으므로 뿌리가 같다. 산출물을 받아 올 토큰이 장비에 있어야 하고, 브랜치를 시험하려면 CI 를 기다려야 한다. 같은 좁힘은 `allowed_signers` 로 장비 빌드에서도 얻는다. 보관소는 root 가 놓은 패키지 파일을 받으므로 나중에 이 길을 더해도 설치, 검사, 되돌리기는 그대로다.
- **끝날 때까지 기다리는 호출 하나.** 호출자에게는 가장 단순하다. 하지만 빌드가 MCP 의 제한 시간을 넘고, 연결이 끊기면 ctl 이 설치와 검사 사이에서 죽어 되돌리기가 일어나지 않는다.
- **잠금 파일(flock)과 작업마다 다른 유닛.** 같은 일을 하지만 잠금과 유닛 둘을 맞춰야 한다. 이름이 고정된 유닛 하나는 systemd 252 에서 두 번째 `systemd-run` 을 바로 실패시킨다(Rocky 9 컨테이너에서 확인).

## 결과

- MCP 의 deploy 한 번이 ref 를 받아 빌드하고, 깔고, 검사하고, 떨어지면 이전 패키지로 돌아온다. 깨진 커밋을 올려도 서버는 앞의 판으로 돌아와 돌고, `/etc/ztgate` 는 바이트 그대로다. `test/deploy_check.sh` 가 이것을 러너의 systemd(deb)와 Rocky 9 컨테이너(rpm)에서 실제로 돌린다.
- 예전 `install.sh` 배치의 장비는 `packaging/migrate-to-package.sh` 로 한 번 옮겨야 자동 되돌리기가 선다. 옮기기 전에는 `no_revert` 를 밝혀야 배포가 된다. 운영 서버처럼 꾸민 Rocky 9 컨테이너(9272113 의 `install.sh` 배치, 콘솔은 `-l 10.0.0.1:9470`)에서 `--apply`, `--undo`, 다시 `--apply` 를 돌려 유닛의 출처, 콘솔의 주소, `/etc/ztgate` 의 바이트를 확인했다.
- 빌드는 1 CPU (`cpu.max` 100000/100000), 765MB 로 묶은 Rocky 9 컨테이너에서 세 번 3.7 ~ 4.2초, 익명 메모리 최고 144MB, `memory.peak` 156MB(파일 캐시 포함), OOM 0 이었다. 이 PC 의 데스크톱 CPU 에서 잰 값이라 운영 장비의 vCPU 에서는 몇 배 느릴 수 있다(추측). `MemoryMax=450M` 은 세 배쯤 여유다.
- `systemd-run --wait` 는 D-Bus 시스템 버스가 있어야 한다. 운영 서버(Rocky 9)와 CI 러너에는 있다. dbus 가 없는 최소 컨테이너에서는 가져오기 단계에서 `failed` 로 멈춘다(장비 그대로).
- 받아들인 맞바꿈.
  - 배포기와 MCP 서버는 `deploy` 로 올라가지 않는다. 고치려면 사람이 `mcp/install.sh` 를 다시 돌린다. 새 ctl 에 생긴 명령도 그때 MCP 에 보인다.
  - 운영 장비(1 CPU)에서 빌드한다. 빌드 동안 VPN 의 지연이 얼마나 느는지는 재지 않았다. `CPUWeight=10` 과 `Nice=10` 으로 양보한다.
  - 작업이 설치 뒤에 끊기면(재부팅, kill) 대상 패키지가 깔린 채 남는다. 그 판이 검사를 통과했는지는 알 수 없다. `deploy_status` 의 `interrupted` 와 그 단계(`installing`, `checking`)를 보고 `deploy_rollback` 을 고른다.
  - 재부팅으로 끊긴 작업은 스스로 되돌리지 않는다. 사람 없이 부팅 때 패키지를 바꾸는 것이 더 위험하다고 본다. `interrupted` 를 보고 사람이나 AI 가 고른다.
  - 세션 수는 판정에 쓰지 않으므로, 클라이언트가 실제로 다시 붙는지는 검사가 보장하지 않는다.
  - 웹 콘솔에는 배포 단추가 없다. 콘솔은 웹에 열린 root 프로세스라, 거기에 "원격의 아무 커밋을 root 로" 를 더하면 콘솔 계정 하나가 장비의 root 가 된다.
  - 운영 서버의 MCP 계정(`woo`)은 NOPASSWD 로 모든 sudo 를 가진다. 그래서 위의 "MCP 계정을 차지한 쪽" 의 한계는 그 계정에는 아직 의미가 없다. 전용 계정으로 나누는 것은 따로 할 일이다.
  - 설정 파일의 모양이 바뀌는 판을 배포기는 알아채지 못한다. 이중화에서 "부 서버를 먼저" 는 문서의 규칙으로만 남는다.
